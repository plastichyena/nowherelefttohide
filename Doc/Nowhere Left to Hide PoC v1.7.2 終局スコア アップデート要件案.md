## 3. 3指標の推奨定義

Hの対象範囲と、初期施設を終局時点で評価し再奪還を対象にする方針は承認済み。部隊点・施設の具体条件は実装用の推奨前提であり、明示決定と技術判断の区別は§11にまとめる。

### 3.1 H：プレイヤー管理下の健康な人間の数

敗北回避用の民間人口より広く、次の互いに重ならない所在地を合算する。

```text
H =
  Player所有施設の workers の合計
  + 生存する味方Human Unitの population の合計
  + 未完成の有効な編成予約の population の合計
  + 全Checkpointの waiting + screening + approved の合計
```

- 都市住民、基地Worker、生産施設Worker、建設施設の健康人口を含む。施設に感染者が併存していても、残る `workers` は数える。
- 搭乗部隊は `state.units` の同じUnit IDを1回だけ数える。輸送機の `cargoUnitId` から人口を再加算しない。
- `healthyCivilians`、`unitPopulation`、兵種別人口、`facilityWorkers` は上記の集約・部分集合なので重ねて加えない。特に現行 `unitPopulation` は編成予約を含む。
- Checkpointの感染者と感染猶予は加算しない。現行の潜伏感染処理は発症分を健康プールから `infected` へ移す。将来の発症をスコア計算のために抽選・予測しない（[engine.ts](../src/core/engine.ts) 565–620行、現行仕様18.13.4）。
- HPが減っていても、生存Human Unitの人数は保存された `population` を使う。HP割合から人数を推定しない。
- 初期中立施設の未救出Survivor、州外へ拒否・退出した人、未到着者、まだ出現していない報酬部隊、死亡者、Zombieは含めない。この対象範囲は2026-10-29の回答2で承認済み。
- この定義では都市間移住、Worker配置、徴用・編成予約、搭乗・降機だけでHが増減しない。編成完成はHを維持したまま表示用の生存隊数Uを増やし得るが、新案では新編成に部隊点を与えない。

未救出Survivorを含める案は今回採用しない。未確保Survivor正値の公開境界も維持する（現行仕様7.4・15章）。人口の場所・職業を変えてもHは同じであることを必須にする。部隊点の水増し防止は§3.3、過密の参考表示と限界は§3.4・§7で扱う。

### 3.2 F：終局時点で健全な初期配置施設の数

初期施設の母集団は `state.map.facilities` のID集合。現在の施設一覧全体や初期Player所有8施設だけを母集団にしない。標準の分母Fmaxは28。州都も1件とし、施設Typeによる点差を付けない。

**終局時の状態を使い、再奪還を対象にする方針は承認済み。** 過去の陥落回数・陥落期間は追加減点せず、再奪還回数を累積加点しない。同じ施設は終局時に最大1件である。「一度も陥落していない施設」への変更や、直前Turnの最小施設数を使う方式は今回採らない。

具体化のため、次の**所有・非感染・再確保済みの施設を数える条件**を実装用の推奨前提とする。ユーザーがrecovering・空施設等を個別に承認したという意味ではなく、再奪還評価と1人配置による稼ぎ防止を両立するための設計判断である。

```text
初期manifestのIDに該当
かつ owner == 'player'
かつ status == 'owned'
かつ infected == 0
かつ operationalStatus が building / disabled / ruined / infected ではない
```

| 終局時の状態 | 推奨候補でのF | 理由・承認上の注意 |
| --- | ---: | --- |
| 所有・非感染・operational | 1 | 基本対象 |
| 感染者が残る／ruined／disabled | 0 | 未陥落というだけでは健全とみなさない提案 |
| 無所有の未陥落施設 | 0 | プレイヤーが確保していない施設を保全成果として数えない提案 |
| 再奪還成功後のrecovering、感染0・所有済み | 1 | 取り戻した施設を終局で評価する回答を重視。機能再開が翌Turnでも数える提案。完全稼働まで要求する別定義なら0になるが、本案は再確保済みを評価する前提 |
| 健康人口0の空施設、stopped、電源OFF・未給電・Supply外 | 所有・非感染・非disabled等を満たせば1 | 人口や給電操作だけでFを増やさず、施設の保全と現在の生産量を分ける提案 |
| 途中建設施設・Checkpoint・有刺鉄線 | 対象外 | 同じTypeでも初期manifestに含まれるものだけが対象 |

健康Workerを「1人以上置く」「一定人数以上残す」ことをFの条件にしない。そうすると終局直前に1人ずつ配って施設点を得る誘因を作るためである。全施設へ同じ最低人口を課す案も、Worker 0が正常なWindや基地の規則に合わない。

現行コードでは、人口撤収で通常施設がstoppedになり、再奪還直後にはrecoveringとなる。これらは陥落と同義ではない（[engine.ts](../src/core/engine.ts) 410–456・3020–3027行、[economy-query.ts](../src/core/economy-query.ts) 74–83行）。単に `operational` だけを数えると、人口操作・復旧待ち時間による点差が生じる。この候補は施設の生活維持能力全体を保証する定義ではない。

初期ID欠落・重複等はデータ整合エラーとして検出する。欠落を黙って0件扱いしない。Fの母集団と終局評価だけなら過去の陥落台帳を新設する必要はない。

### 3.3 部隊点B：初期配置部隊の健康人員維持率（推奨前提）

**全生存部隊の頭数を直接加点せず、開始時の部隊人員をどれだけ残せたかを点にする案を推奨する。** これは元の全生存隊数という採点範囲を狭める設計上の前提であり、ユーザーが対象部隊を個別指定した事実として扱わない。新編成頭数による稼ぎを抑えるという最新方針に合わせた具体化である。 最初の部隊は双方のマップモードで固定7隊、標準合計45人である（現行仕様672行付近、[initial-deployment.ts](../src/core/initial-deployment.ts) 21–30行）。

- 開始時に、初期Human UnitのID・初期populationを固定する。I0はその人口合計。
- 終局で同じIDの味方Human Unitが生存している場合だけ、初期populationと終局populationの小さい方を合計してIとする。IDの再利用や新編成への引継ぎで初期部隊を復活扱いしない。
- 仮の部隊点は `B = I0 > 0 ? floor(50 × I / I0) : 0`。範囲は0～50点。
- 新編成・増援・報酬部隊はHと全生存隊数Uには含めるが、Bを増やさない。編成予約・完成・搭乗・降機だけではHもBも増えない。初期部隊が搭乗中でもIDごとに1回だけ数える。
- customで初期部隊人口が0ならB=0。人口0の隊を大量に作っても点は増えない。分母I0を死亡・感染・兵種変更・ロードで縮めない。
- 表示用Uは、生存する味方Human UnitのユニークID数。輸送機と搭乗部隊は別々に1隊、予約・未出現部隊・Zombie・軍用ドローンは除外する。U自体は点数に掛けない。

10人の1隊と5人の2隊を同じ10人として扱うため、隊の細分化ではBを稼げない。現行に任意の即時分割Actionは確認していない。実際の比較対象は兵種・編成数・完成待ちであり、存在しない操作を検証済みとはしない（[engine.ts](../src/core/engine.ts) 2853–2881・3717–3744行、[unit-lifecycle.ts](../src/core/unit-lifecycle.ts) 56–77行）。

この案は初期部隊の温存を促す一方、新たに編成した部隊には独立した生存点を与えない。新部隊の健康人口はHで等しく評価する。原要件の「生存隊数そのものへの加点」を完全に維持した対策ではない。前稿のFinal時点の部隊登録案は、登録前の大量編成で稼げるため推奨から外す。

### 3.4 過密は終局時の参考情報だけ

終局時のPlayer所有Capital / Cityについて、既存Queryと同じ`N = workers + infected`、`C = workerCapacity`、`E = max(0, N-C)`を表示用に使う。必要なら都市別の収容人数・容量・超過人数と合計をsnapshotへ含める。感染者を含む都市の混雑指標であり、健康人口Hや実際の被害人数とは区別する。

Eは点数・敗北控除・順位・同点決着・採点対象資格のいずれにも使わない。健康な人間を過密だからHから除外したり、部隊・検問所へ架空の都市定員を追加したりしない。過密に応じて勝敗やゲーム進行を変更しない。

過去に混み合っていても終局で解消していれば現在の過密は0。最終ターンの救出や通常移住で過密が残っても、点数には影響しない。「救出か意図的詰め込みか」の採点上の識別、履歴台帳、猶予カウンタ、未来の生活状態の予測は不要である。

### 3.5 現行処理から確認できることと限界

中立生存者の救出は`tryCapture`の`available → rescued`と`survivors_rescued`で識別でき、再奪還とは別である。[engine.ts](../src/core/engine.ts) 410–468行。避難民の配置には`screening_approved / approved_refugees / unmanaged_pass_through`の理由と人数がある。同532–620・673–705行。

一方、`TransferPopulation`は健康人口を安全な適格都市間で移し、`city_transfer`を記録するだけで、緊急避難と意図的詰め込みの意図は識別できない。同3041–3119行。所在地人口も個人由来を保持しない。[types.ts](../src/core/types.ts) 229–255・382–402行。これを無理に救出認定へ転用しないことが今回の明示決定に合う。

現行StateからH・F・表示U・現在の過密を求められ、保存済みの実Map・Configと既知の初期配置規則から初期部隊基準を確認できる。新設が必要なのは採点版・係数と開始時基準、不変の終局結果である。将来の生存人数や人道性の判定は新設しない。

## 4. 実装用の推奨式と調整可能な係数

### 4.1 式・既定値・係数の契約

以下の値は**ユーザーが数値指定したものではなく、実装案の推奨既定値**である。過密項は式に存在しない。

```text
wH = 100  # 健康な人間1人
wF = 300  # 健全な初期施設1件
bMax = 50 # 初期部隊の人員維持点の最大値

B = I0 > 0 ? floor(bMax × I / I0) : 0
A = wH × H + wF × F + B
P = wH × Hmax + wF × Fmax + bMax + 1

勝利 S = A + 1
敗北 S = A - P
```

施設1件は人口3人分の重みであり、厳密な辞書順ではない。標準開始時H155なら人口点15,500、施設全28件でも8,400点となり人口を主軸にする。ただし、全ての終局状態で人口点が最大割合になるとは保証しない。

係数はCore側の一箇所で管理し、開始時に実際に使用する値を採点Contextへ固定する。保存・比較条件に含め、途中変更やロード後の既定値変更で同じプレイを再採点しない。Configへの追加キー・型名・配置先は既存の検証方針に合わせる技術判断とし、係数調整用UIは要求しない。

推奨する検証制約は、wH・wFが正の整数、bMaxが非負整数、`bMax < min(wH, wF)`。これにより部隊点の全差だけでは健康者1人または施設1件の損失を埋められない。人口重視という意味が変わるほどの比率変更は、単なる不具合修正として黙って行わず、別の調整値・比較条件として明示する。

### 4.2 範囲、敗北符号、ゼロ・極端値

`0 <= H <= Hmax`、`0 <= F <= Fmax`、`0 <= I <= I0`、`0 <= B <= bMax`なら、`0 <= A <= P-1`。よって勝利は1..P、敗北は-P..-1となる。

同じ係数・比較条件・他の採点入力でHが1増えればwH点、Fが1増えればwF点上がり、敗北でも負値の絶対値が小さくなる。Bは切捨て丸めにより小さな維持率差が同点になる場合があるが、その健康人員はHへ等しく含まれる。敗北を単純な`-A`にしない。

Hmax / Fmaxは開始時に固定する。途中の死亡・感染・実到着人数でPを縮めない。都市Soft Capを総人口上限にしない。既存の流入源に基づく保守的な上限案は次の合計である。

- 初期施設数×初期施設Typeの最大workerCapacity＋初期Human Unit人口。初期配置はworkers＋infectedがcapacity以下と検査され、中立も含む安全側の上限を取る。
- 支線数×ceil(Final Turn／最小到着間隔)×Final Turnでの到着人数上限。Final後の新規到着停止を利用し、Final同Turnの処理を含む安全側の上限とする。
- Army Baseの一度限りのSoldier報酬と、原発・Air Baseの一度限りのSpecial Forces報酬の人口。通常の徴用・編成は人口移動であり流入にしない。

根拠: [state.ts](../src/core/state.ts) 343–375・517–525行、[refugees.ts](../src/core/refugees.ts) 4–8行、[engine.ts](../src/core/engine.ts) 254–262・338–383・738–757・2552–2557行。

標準Configでの仮計算は次のとおり。

```text
初期人口上限 = 28 × 100 + 45 = 2,845
到着人口上限 = 4 × ceil(70 / 2) × (20 + floor(69 / 2)) = 7,560
増援人口上限 = 10 + 5 + 5 = 20
Hmax = 10,425、Fmax = 28、I0 = 45
P = 1,050,951
```

実到達可能な最大値や全custom構成の網羅的証明ではない。実装時に流入源とConfig制約を照合し、有限上限を証明できないcustomは「採点未対応」と理由を明示する。標準上限を黙って流用せず、通常の標準プレイは必ず採点できることを受入条件とする。

H・F・I等が負数・小数・非有限・範囲外なら不正を検出し、clampや0点で隠さない。計算は任意精度整数、A/P/Sや大きな上限は保存時に10進整数文字列を推奨する。既存のNumber値はsafe integerを確認して変換し、既に精度が失われた値をBigIntで復元できるとは扱わない。BigIntオブジェクトをJSONへ直接入れない。I0=0ならB=0とし、人口0の部隊頭数で点を増やさない。

### 4.3 算術例

I0=45、推奨係数とP=1,050,951による例。過密値が違っても以下の点数は変わらない。実ゲームで全組合せに到達できるという意味ではない。

| H | F | I | B | A | 勝利S | 敗北S |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 300 | 20 | 45 | 50 | 36,050 | 36,051 | -1,014,901 |
| 301 | 20 | 45 | 50 | 36,150 | 36,151 | -1,014,801 |
| 300 | 21 | 45 | 50 | 36,350 | 36,351 | -1,014,601 |
| 300 | 20 | 0 | 0 | 36,000 | 36,001 | -1,014,951 |
| 0 | 0 | 0 | 0 | 0 | 1 | -1,050,951 |

全入力0の勝利1は数式上の境界であり、人口0即敗北のゲームで0人勝利を認める変更ではない。州都陥落時のFは最大27。実際の勝敗理由と両立するCoreケースは、算術だけの境界とは分けて検証する。

## 5. 敗北と州都ペナルティ

州都陥落を含む有効なゲーム内敗北へ、共通控除Pを1回だけ適用する案を維持する。州都陥落では州都がFから失われ、さらに敗北の符号へ移る。原因別の追加控除は設けない。

| 終局・停止 | 提案する扱い |
| --- | --- |
| won / stateSecured | A+1。Final以外の敵の残存自体を新たに減点しない |
| lost / capitalLost | 必須の陥落連鎖を完了した終局値でA-P |
| lost / healthyCiviliansLost | 部隊・編成待ち・検問所にHが残っていてもA-P。州都陥落と偽って表示しない |
| 両敗北条件の同時成立 | 現行どおりcapitalLostを主理由とし、控除は1回 |
| abandoned / error | 型にはあるが、確認したCoreの正式終局は上記3種。将来有効なlostを発行するなら同じ負値式とし、通常記録と区分 |
| 途中終了・Runner上限・技術失敗・拒否Action | 正式な終局結果がなければ未採点。架空の敗北や0点を作らない |

「州都ペナルティ」は敗北共通控除と州都施設点の喪失を意味する提案であり、人口0敗北を州都陥落という事件へ読み替えない。既存の勝敗判定や原因の優先順位は変更しない。

## 6. 実装範囲と終局確定

推奨する責務は次の3つに限定する。関数名・型名は例で、既存のCore境界へ合わせてよい。

1. **開始時基準の生成**：初期配置・Config確定時に採点版、固定係数、初期施設ID、初期部隊IDと人口、I0、Hmax/Fmax、比較条件を作る。毎Actionのスコア更新や救出履歴は不要。
2. **純粋な終局計算**：正データからH・F・I・Uを重複なく導出し、勝敗と基準から点数を返す。参考の終局過密は別項目とし、score計算へ渡す必要はない。ゲーム進行・感染抽選・RNGに副作用を持たせない。
3. **結果への固定と利用**：終局理由と仕様上必須の原子的連鎖を完了し、人口同期後の値をGameResultの不変snapshotへ入れる。GameActionのcandidate検証・commitが成功した場合だけ公開・保存し、拒否candidateの結果は破棄する。UI・保存・Session出力は同じsnapshotを使う。

実装候補はCoreの型・採点用小モジュール・初期化・finishGame境界、保存検証と互換処理、終局表示の内容接続。具体的なファイル分割は技術判断である。既存の資産状態や戦闘、移住、徴用、救出、勝敗条件を変えない。

[engine.ts](../src/core/engine.ts) 2666–2676行のfinishGame後に、外側4674–4678行の共通処理が呼ばれ得る構造は既存の確認事項。実際に値が変わる不具合を再現した結果ではない。実装担当は、必要な陥落・報酬等の連鎖が終わった境界で凍結し、終局後の共通処理が対象を変えないことを限定確認する。必要ならこの境界だけを整える。

終局後の演出・再表示・言語変更・Load・Action拒否で再採点しない。現在StateからUIだけが再集計して上書きしない。追加EndTurnを実行して終局後の食料不足・過密感染を発生させることもない。

## 7. 水増し防止と残る限界

| 比較・操作 | 採用案の扱い |
| --- | --- |
| 都市間移住、Worker配置、徴用、予約完成、搭乗・降機 | 同じ人はHに1回だけ。新編成でBを増やさず、施設の所有・感染等が同じならFも同じ。過密や職業の変更だけでは総点を増やさない |
| 50/50→1/99の都市移住 | H/F/Bが同じなら同点。参考の都市過密は0→49。既存の追加費はFood25・民需品98／EndTurnだが、スコア減点や追加EndTurnを行わない |
| 最終ターンの救出・既存住民の緊急避難 | 過密による減点なし。未救出中立から健康者が管理下へ入ればHで評価し、既にHに含む検問所から都市への配置では二重加点しない |
| 救出の自己申告・受入れ時刻の調整 | 免除制度自体がないため免除点は作れない。猶予切れを避けるための終了時刻の誘因も新設しない |
| 10人1隊と5人2隊、新編成の大量生産 | 初期部隊人員基準で評価し、表示Uを直接加点しない。初期I0=45なら採点対象10人はどちらもB=11。新兵で失った初期部隊点を復活させない |
| Hを1減らして隊数を増やす | 同じFで人口点100を失い、Bの全幅50でも埋められない。過密減点の軽減や足切り通過による利益は存在しない |
| 空施設に1人だけ置く | 推奨F条件ではWorker数だけでFが変わらず、1人配りの施設点を作らない |
| 初期施設を失って再奪還 | 終局時に健全条件を満たせば1件。過去の陥落や再奪還回数を加減点せず、二重加点しない |

施設との交換は重み付き採点に残る。I=45ならH301/F1の勝利点30,451よりH300/F28の38,451が8,000点高い。一方、H300/F20からH299/F21へ変わると、人口1人を失っても施設1件で200点上がる。これは係数が許す交換であり、意図的な使い捨てを全て排除した証明ではない。

過密を参考表示に限定した結果、同じH・F・Bなら、安定した分散居住と終局直前の詰め込みを点数で区別しない。これは救出・避難を罰しないための明示決定の限界として記載し、隠れた順位条件で再び減点しない。

軍人の飢餓対象の違い、都市へ受け入れる前の検問所滞留、食料・民需費・感染・防衛の長期的な差、施設撤退の是非は既存ゲームの結果へ影響し得る。スコア項の削除や頭数対策だけで、すべての戦略上の報酬ハックを封鎖したとはしない。新たな健康シミュレーションや移住制限で補わない。

時間・撃破・生産累計・再奪還回数・HP割合は加点せず、同じ採点入力は同点とする。新しい大量編成を待つだけのB加点はない。

### 7.1 比較条件

難易度・マップ倍率は新設せず、採点版、係数、Rules版、scenario、完全Config識別、mapMode / mapHash / 生成版、rootSeed / mapSeed / gameplaySeed、fallback、初期配置条件が一致する記録同士を厳密比較する。

MapDescriptorのsettingsIdだけでは完全Configを識別できない（[map-generation.ts](../src/core/map-generation.ts) 14–55行）。完全Configの正規化識別と開始条件を含め、非公開のSurvivor正値・初期敵位置は表示しない。UNA/custom、異なるSeed・I0・Hmax・係数は同じ公平な順位表へ混在させず、参考比較と明示する。特にPが違う敗北点を直接順位づけしない。

同条件でも乱数消費は操作順に依存する。単一Seedを普遍的な実力評価とせず、オンライン順位表や複数Seed競技評価へ拡張しない。

## 8. 保存と既存データ互換

### 8.1 新規データの保存契約

採点版の仮称は`terminal-assets-v1`。実際の型名は例として、開始時の`scoreContext`と、結果の`terminalScore`を分ける。

- 開始時Context：採点版、wH/wF/bMax、初期施設ID、初期部隊IDと人口・I0、Hmax/Fmax、比較条件。固定されたMap・Config等から導出する情報は正データとの一致を検証する。
- 終局snapshot：Hと所在地別内訳、F/Fmax、表示U、I/I0、各加点、A/P/S、採点版・係数・比較条件、参考の終局過密。勝敗・理由・Turnは既存GameResultを正本とする。
- 大きな整数は10進文字列、既存のJSON互換形式を維持する。scoreを同じ版・係数・入力から再計算して一致を検証する。参考過密は計算へ入れない。
- 新規v1.7.2の有効な終局にはscoreが必須。旧結果・採点未対応は理由付きの明示状態とし、0点に置き換えない。新規データの必須項目欠落を旧版扱いで逃がさない。
- 救出や過密の履歴、猶予、免除記録は追加しない。中間案で必要だった過密由来の互換条件も不要。

終局自動保存と手動保存の共有1枠は維持し、score専用DBを増やさない。保存失敗時はメモリ上の確定結果を保持して未保存と表示し、成功済みデータを壊さず再試行可能にする。過去結果の保管には既存のSaveコード／JSON出力を利用する。

### 8.2 v1.7.1の限定互換を目標にする

現行はApp 1.7.1、Rules/State/Config 20.0.0、Save 27でApp版完全一致検査がある。無条件にこの検査を外さず、旧データの検証後に明示的に移行する。[versions.ts](../src/core/versions.ts)、[save.ts](../src/persistence/save.ts) 1382–1456行。

| データ | 推奨する扱い |
| --- | --- |
| v1.7.2新規・同版途中Save | 開始Contextを保存し、終局で一度だけ採点。同じ行動列・同じ採点条件なら同じ結果 |
| v1.7.2同版終局Save/Session | 終局snapshotを検証して復元し、LoadSnapshot等のゲーム操作を進めず表示・出力 |
| v1.7.1途中Save | 保存された実Map・Configとv1.7.1の固定初期配置規則から、初期施設・元の部隊ID/人口・上限を再構成してContextを付与する限定移行を推奨。以後の終局は採点可能。過去の救出履歴は不要 |
| v1.7.1終了済みSave | 既存結果は表示し、scoreは「旧版・未計測」。過去の厳密な凍結時点を保証できないため、現在Stateから遡及採点した値を正規記録にしない |
| v1.7.0以前 | 既存の非破壊拒否を維持 |

旧途中Saveの基準は、**現在生存している部隊から逆算しない**。死亡した初期部隊もI0に含め、[initial-deployment.ts](../src/core/initial-deployment.ts)と対応版Configによる元の基準を使う。認識できない初期配置・Config・人口上限なら、基準を捏造せず理由付きの非破壊拒否または継続可能な未採点扱いとする。どちらの既存エラー経路へ接続するかは実装時の技術判断とし、互換の実績を正確に報告する。

移行では地図・敵・人口・RNG・資産・既存結果を再生成しない。v1.7.1の元Saveと旧autosave枠を保持し、v1.7.2は新しい名前空間を使う案とする。旧Saveの存在だけで強制移行・上書きしない。

旧Session / Checkpoint / Replay / 公開ArtifactはSaveと別境界で、形式ごとの検証なしに旧版対応を宣言しない。同版の終局復元・出力は受入対象とする。Rules/State/Config/Save番号の具体値は実装差分と既存方針に合わせる技術判断であり、ここでは番号を先決めしない。

既存v1.7.1確定要件の互換努力目標を維持する。旧途中Saveの移行は上記の具体案を実装・検証して可否を報告し、未検証のまま互換を保証しない。対応できないケースを理由なしに正常採点として通さない。

## 9. 表示の内容要件

勝利／敗北、符号付きscore、実際の理由、終局Turn、採点版・係数、保存状態を表示する。内訳は健康人口H、健全な初期施設F/Fmax、初期部隊人員I/I0とB、敗北控除-Pまたは勝利の+1、合計を確認できること。

全生存隊数Uと点になる初期部隊人員Iを区別し、新編成の健康人口もHへ含むことを説明する。人口0敗北を州都陥落と表示しない。0・旧版未計測・採点未対応・不正入力・保存失敗を区別し、整数を丸めて別順位に見せない。

過密は「終局時の参考情報・スコアへの影響なし」と明記する。終局の都市人数・容量・超過人数を必要な範囲で示し、感染者を含むことを健康人口Hと混同させない。過密を減点・不正認定・隠れた順位条件として表示しない。解消済みの過去最大値や免除期限の表示は不要。

比較条件、custom/fallback、旧Save由来を識別する。日英で同じ意味と数値、タイトルはNowhere Left to Hide。既存の食料・民需費情報を併記しても未来の確定死亡としない。配置・色・画面構成・アニメーション・エフェクト等は既存Claude担当方針を変更せず、内容要件だけを定める。

## 10. 最小の受入条件（次工程で実装・検証）

今回は試験コードやゲーム実装を作らず、以下を次工程の受入条件とする。

1. **人数保存と頭数稼ぎ防止**：所有施設、部隊、編成予約、Checkpoint各健康プールを合計してHを確認。移住・徴用・予約完成・Worker配置・搭乗／降機で二重計上や総点増がない。感染・死亡でHが減り、新編成・人口0部隊・増援の頭数でBを増やさない。I0を損失で縮めない。
2. **施設の境界**：初期IDだけを対象とし、無所有・感染・ruined・disabledは0、推奨前提では再奪還recovering・空stoppedは1。Worker0→1、電源操作、建設・再奪還回数で水増ししない。母集団欠落・重複を検出する。
3. **過密非採点**：同じH/F/Iの50/50と1/99、最終ターン救出・通常移住の緊急避難、解消前後でscoreが同じ。参考の過密値だけが変わる。履歴・猶予・免除の有無やイベント数で点数を変えない。採点のための追加EndTurnやRNG消費がない。
4. **数式・係数・極端値**：HまたはFの単独増加で勝利・敗北とも高得点。H1人減をB全幅で埋められない。0、上限、I0=0、人口0兵種、大きな整数、範囲外・不正値を扱う。標準の全人口流入をHmaxへ含め、対応customも上限を確認する。係数変更後の新規プレイと旧保存結果を混ぜない。
5. **実Core終局**：Final Pending中は未採点、最後のFinal消滅で勝利。州都陥落の必須連鎖後、健全民間人口0、両条件同時成立を分け、Hが残る人口0敗北も必ず負。拒否Action・Runner上限で架空の結果を作らない。外側共通処理や演出でsnapshotが変わらない。
6. **保存・互換**：新規/途中/終局の同版Saveコード・JSONと終局Sessionで値を維持。保存失敗と再試行でもメモリ結果は同じ。v1.7.1途中Saveでは正しい初期基準を再構成し、既に死亡した初期部隊で分母を減らさない。旧終局は未計測。旧データ・RNG・Mapを改変せず、v1.7.0以前は非破壊拒否。
