# 1. 文書の位置づけ

本書は、v1.3.3のSol Medium敗北Replay分析と、その後の設計検討を踏まえたv1.4.x系アップデートのドラフト案である。

本書の目的は、次期大型更新の方向性を固定しつつ、実装前に必要な数値・境界・API変更・テスト観点を整理することにある。

本書に記載された内容は次の3区分で扱う。

- **確定方針**: v1.4.xで導入する前提の要素
- **推奨初期値**: Playtest開始時の候補値。実装前後のSimulationで変更可能
- **未確定項目**: 本ドラフトでは結論を固定しない

現行v1.3.3の正本は引き続き `Doc/Nowhere Left to Hide PoC 現行仕様.md` とする。本ドラフト採用後に正式要件へ昇格し、実装完了時に現行仕様へ統合する。

# 2. 背景

v1.3.3 Sol Medium敗北Replayでは、戦術上は最終盤まで防衛が成立していた一方、唯一の主力Farm喪失後に食料生産を再建せず、最終的に資源不足による健全民間人口0で敗北した。

主な観測事項:

- Unit損失は限定的で、Final Hordeも大部分を撃破していた。
- Checkpoint Automatic Fallbackは複数回正常に機能し、v1.3.3の行政冗長化は実戦上の価値を示した。
- 一方、食料生産は単一Farmへの依存が続き、代替生産手段がなかった。
- 復旧済みFarmへ労働者を戻せば即時敗北を回避できる局面でも、Sol Mediumは戦闘を優先した。
- Checkpoint前進の一部はSupply半径を実際には拡張せず、前進の戦略価値がObservationから直感的に読み取りにくかった。
- Strict運用ではCheckpoint人口Queueが大きくなり、前線Population TargetとしてのRiskが増える可能性がある。

v1.4.xではこれを単純な資源緩和ではなく、

> **広い戦域・高速機動・燃料兵站・前線インフラ・生産冗長性・広域索敵**

へ発展させる。

# 3. v1.4.xのテーマ

> **Operational Depth / Logistics / Forward Infrastructure / Strategic Readability**

v1.4.xでは、Playerへ次の新しい判断を要求する。

- 広いMapで、全戦線へ同時対応できない前提で部隊を配分する。
- 高速移動は可能だが、長距離移動ではFuelを消費する。
- Fuelを発電と軍事機動のどちらへ使うか判断する。
- Supply内へ簡易施設を建設し、恒久施設の喪失に備えて冗長性を作る。
- Droneによる広域Visionを使い、敵が接触してからではなく接近段階で戦場を選ぶ。
- Checkpoint、Supply、Forward Facilityを一体の作戦線として扱う。
- ForecastとDependency情報を使い、戦術的勝利より確定的な国家崩壊回避を優先する。

# 5. Map拡大

## 5.1 最低要件

- Mapは30×30以上へ拡大する。
- 固定Mapの考え方は維持し、Random Mapは本Versionの必須要件にしない。
- Terrain、Road、Facility、Horde Entrance、Road Branch、Supply Sectorを新Mapへ再定義する。

## 5.2 推奨Map Size

**31×31を推奨初期値とする。**

理由:

- 単一の中央Hexを持てる。
- 州都を `(15,15)` に配置できる。
- 東西南北の端まで各15Hexで完全対称になる。
- 現行15×15の中心構造を拡張しやすい。
- Road Branch、Horde Entrance、Sector、Replay Testを対称条件で管理できる。

推奨中心構造:

```text
Capital: (15,15)
North Entrance: (15,0)
East Entrance: (30,15)
South Entrance: (15,30)
West Entrance: (0,15)
```

31×31の場合、Map総Hex数は961となり、現行225Hexの約4.27倍となる。

## 5.3 Map設計方針

- 州都から各主要方向へ幹線道路を延ばす。
- Road Branch数は固定4に限定しない設計を維持する。
- Constructible Facility上限等はRoad Branch数から一般化する。
- Terrain比率は現行Mapの単純4倍コピーにせず、長距離移動・索敵・防御地点形成を意識して再配置する。
- Urban Defenseを得られる恒久Facility地点は、長距離戦で意味のある間隔へ配置する。
- Supply拡張に価値が生じるよう、初期Supply Radius外にも重要施設を複数配置する。

# 6. Human Unit移動力拡張

## 6.1 移動力

Police、National Guardの標準Movement Budgetを現行5から**10**へ引き上げる。

Zombie / Horde ZombieのMovementは本ドラフトでは変更しない。

```text
Police Move Budget = 10
National Guard Move Budget = 10
Zombie = 現行維持
Horde Zombie = 現行維持
```

Map拡大に対し、Human Unitだけが広域再配置能力を持つことで、Player側のOperational Mobilityを強化する。

## 6.2 Terrainとの関係

移動可能距離は現行どおりTerrain Movement Costの累積で判定する。

```text
Path Movement Cost <= Unit Movement Budget
```

Fuel消費はTerrain Costではなく、**実際に進入したHex数**を基準とする。

これにより、

- Terrain = 時間・機動性
- Fuel = 距離・兵站

として役割を分離する。

# 7. Unit Fuel Pool

## 7.1 基本概念

Police、National Guardは各Unit固有のFuel Poolを持つ。

Fuel Poolは州のResource Fuelとは別のUnit内部在庫であり、補給時に州在庫から補充される。

Observationでは各Unitについて最低限次を公開する。

```text
currentFuel
maxFuel
fuelCostForSelectedMove
projectedFuelAfterMove
inSupply
projectedRefillDemandIfTurnEndsNow
```

## 7.2 移動Fuel消費

移動しない場合はFuelを消費しない。

1～5Hexの移動はUnit Typeを問わずFuel 1固定とする。

### Police

```text
1-5 Hex = 1 Fuel
6 Hex = 2
7 Hex = 3
8 Hex = 4
9 Hex = 5
10 Hex = 6
```

式:

```text
distance == 0 -> 0
distance 1..5 -> 1
distance >= 6 -> 1 + (distance - 5)
```

### National Guard

```text
1-5 Hex = 1 Fuel
6 Hex = 3
7 Hex = 5
8 Hex = 7
9 Hex = 9
10 Hex = 11
```

式:

```text
distance == 0 -> 0
distance 1..5 -> 1
distance >= 6 -> 1 + 2 * (distance - 5)
```

National Guardは高速長距離展開が可能だが、6Hex以降のFuel負担をPoliceより大きくする。

## 7.3 Refuel

Player Turn End時点でSupply Network内にいるHuman Unitは、Fuel Poolを最大値まで補充しようとする。

```text
refillDemand = maxFuel - currentFuel
```

補充量だけ州のFuel在庫を消費する。

Supply外でTurn EndしたUnitはFuelを補充しない。

同TurnにRefineryが新規生産したFuelをUnit補給へ使えるかは、現行の「同Turn生産物を別工程入力へ使わない」原則との整合を踏まえて正式要件で確定する。

## 7.4 Fuel Pool容量

未確定。

Playtest開始時の推奨候補:

```text
Police maxFuel = 12
National Guard maxFuel = 22
```

これは最大距離移動を概ね2回行える余裕を持たせる案である。

1回分だけの容量にするとSupply外へ最大移動したUnitの撤退余地が小さすぎるため、初期値としては2回分程度を推奨する。

## 7.5 州Fuel不足時の補給順

未確定。

候補:

1. Unit ID順に満タンまで補給
2. 1 FuelずつRound Robinで公平配分
3. Player指定の補給優先度を導入

v1.4初期実装では、決定的かつ簡潔なRound Robin方式を推奨する。

# 8. Fuelと発電の競合

現行のFuelはPower Plant発電にも使用する。

v1.4では、同じ州Fuel在庫が、

- Power Generation
- Human Unit Refuel

の双方から需要を受ける。

このためPlayerは、

```text
発電を維持する
vs
軍を長距離展開する
```

という新しい兵站判断を行う。

EndTurn Forecastでは最低限、

```text
turnStartFuel
projectedPowerFuelDemand
projectedUnitRefillDemand
projectedTotalFuelDemand
projectedEndingFuel
shortage
```

を区別して表示する。

処理順は正式要件で固定する。

# 9. 初期Wind Power Plant

## 9.1 概要

初期所有施設へWind Power Plantを追加する。

- Worker割当不要
- Worker割当不可
- Fuel消費なし
- Electricity Capacity 15を最低保証
- Player所有状態で開始
- Supply、Vision等の付随効果は通常Facility Ruleに従うか正式要件で確定

```text
Workers = 0 fixed
Power Generation = 15
Fuel Cost = 0
```

## 9.2 Zombie Target

Wind Power Plantは健全民間人口を持たないが、Zombie Target評価上は**人口5のFacility相当**として扱う。

このためCoreでは、実人口とZombie Target Valueを分離できる設計を推奨する。

概念:

```text
healthyPopulation = 0
zombieTargetValue = 5
```

Zombie Target ValueはDefeat条件、Population、Consumptionへ加算しない。

## 9.3 Overrun / Recovery

Wind Power Plant上でZombieがTurnを終了した場合、感染処理ではなく機能停止状態とする。

推奨状態:

```text
operational
-> zombie occupied / disabled
-> human recapture
-> recovering
-> next player turn operational
```

- Zombie占有中は発電0。
- Human Unitによる再確保後、次Player Turnから発電を再開する。
- 無人施設のため通常Facilityの感染者Poolは作らない。
- 通常Facility Overrun時の感染者下限や追加Zombie Spawnを流用しない。

# 10. Constructible Facility共通概念

v1.4でSimple FarmとCivilian Drone Baseを同時追加するため、個別特殊処理ではなく**Constructible Facility**を共通概念として追加する。

共通候補Rule:

- Player Supply Network内だけで建設可能
- 空きHexのみ
- Visible ZombieがいるHexには建設不可
- Facility／Checkpoint／既存Constructible Facilityと重複不可
- 建設時Civilian Goodsを消費
- Player Actionを消費
- 建設したTurnはWorker操作不可
- 次Player TurnからWorker配置可能
- 自身はSupply Sourceにならない
- Powerが必要
- Type別の同時存在上限を持つ
- Save / Replay / Agent Observation / UIへ正式Facilityとして公開

建設可能Terrainは未確定。

初期案:

- Water不可
- Mountain不可または高コスト
- Plain / Forest / Roadは許可

---

# 11. Constructible Facility上限

各Constructible Facility Typeの同時存在上限はRoad Branch数から一般化する。

```text
limitPerType = ceil(roadBranchCount / 2)
```

標準4 Branch Mapでは:

```text
Simple Farm max = 2
Civilian Drone Base max = 2
```

上限はTypeごとに独立する案を推奨する。

FarmとDroneを合算上限にすると「食料か索敵か」の競合が強すぎるため、初期実装では別上限とする。

Destroyed状態の施設を上限に数えるかは、施設が物理的に消滅するRuleに合わせて正式要件で固定する。

# 12. Simple Farm

## 12.1 概要

PlayerがSupply Network内へ建設できる簡易農場。

目的:

- 恒久Farmの代替ではなく、Food Productionの冗長性を作る。
- 単一Farm喪失による即時的な長期崩壊を防ぐ。
- Supply前進に経済的価値を与える。

## 12.2 Worker

```text
Worker Capacity = 10
```

Worker 0～10を配置できる。

## 12.3 Power

Simple FarmはPower Requiredとする。

- Required Power Capacity: 暫定5
- 無給電時の生産: 0
- 給電時のみFood生産

恒久FarmのようなBoost型ではなく、Field InfrastructureとしてPower必須にする。

## 12.4 生産量

未確定。

推奨初期値:

```text
Food 5 / worker / turn
Max 50 / facility
```

4 Branch Mapで最大2施設なら合計100 Food/turnとなる。

これは恒久Farmを完全代替せず、主力Farm喪失時の猶予と最低限の生存性を与える値としてPlaytestする。

## 12.5 Infection / Destruction

Workerが1人以上いるSimple Farmは通常の有人FacilityとしてZombie Attack／Infection対象になる。

健常Workerが感染によって0になりFacilityが陥落した場合、Simple Farmは**同時に消滅**する。

- Ruined Facilityとして永続残存させない。
- 再建には新規Buildが必要。
- 感染者を施設消滅時にどう処理するかは正式要件で固定する。

## 12.6 完全無人時

Worker 0のSimple FarmをZombieが占有した場合、感染対象人口が存在しないため即時Destroyしない。

推奨挙動:

```text
operational empty
-> zombie occupied / disabled
-> human recapture
-> next player turn operational
```

再確保した次Player TurnからWorker配置可能とする。

# 13. Civilian Drone Base

## 13.1 概要

PlayerがSupply Network内へ建設できる監視施設。

- Supplyは提供しない。
- Visionのみを提供する。
- Worker配置人数でVision Radiusが変化する。
- Power Required。

## 13.2 Worker

```text
Worker Capacity = 5
```

## 13.3 Vision

推奨初期式:

```text
Vision Radius = workers * 2
```

したがって:

```text
0 workers = 0
1 worker = 2
2 workers = 4
3 workers = 6
4 workers = 8
5 workers = 10
```

Map拡大に伴い、最大5人で広域Vision 10を提供する。

Visionは現行のShared Visibility Unionへ追加する。

## 13.4 Power

- Required Power Capacity: 暫定5
- 無給電時Vision = 0
- WorkerがいてもPower未供給なら監視機能停止

## 13.5 Infection / Destruction

有人時はSimple Farmと同じConstructible Facility Ruleを使用する。

- Infectionで健常Worker 0になり陥落した時点で施設消滅。
- 再建には新規Buildが必要。

Worker 0時にZombie占有した場合はDestroyせずdisabledとし、Human Unitが再確保した次Player Turnから再利用可能とする。

# 14. Supplyとの関係

Constructible FacilityはSupply Network内にのみ建設できるが、自身はSupplyを延長しない。

```text
Checkpoint -> Supply Frontを決める
Drone Base -> Visionだけ
Simple Farm -> Food Productionだけ
```

これにより、

```text
Checkpoint前進
-> Supply拡張
-> Forward Facility建設可能範囲拡大
-> Droneで索敵
-> Farmで冗長性確保
```

という戦略Chainを成立させる。

Constructible FacilityをSupply Sourceにして連鎖的Leapfrogを可能にすることは禁止する。

# 15. Strategic Readability強化

v1.3.3 Replayでは、Player/Agentが個別の公開情報を取得できても、長期的な国家崩壊Riskを十分に統合できない場面が確認された。

v1.4では、Hidden情報を追加せず、Coreが既に計算可能な公開情報をStrategic Forecastとして整理する。

## 15.1 Critical Resource Dependency

生産Resourceごとに、現在の生産構成と単一障害点を公開する。

例:

```text
Food Production
Farm-1: 230 / 230 = 100%
Warning: Single Point of Failure
```

最低限:

- Resource別Current Production
- Facility別構成比
- 最大Facility喪失時のProjected Production
- Single Point of Failure判定

を返す。

## 15.2 Guaranteed Defeat Forecast

EndTurn実行で確定的にDefeatする場合、通常の不足Warningより上位のCritical Warningとして公開する。

例:

```text
Critical: End Turn causes 106 Food shortage and healthy civilian population reaches 0.
```

Agentはこの状態をCombatより上位の `avoid_defeat` として評価する。

Human UIでも同じCore Forecastを表示する。

## 15.3 Checkpoint Projected Supply Effect

Checkpoint Position Candidateへ、合法性だけでなくAction後の公開Supply差分を追加する。

概念:

```text
currentBranchRadius
projectedBranchRadius
newlySuppliedFacilityIds
newlyUnsuppliedFacilityIds
suppliedFacilityDelta
```

これにより「前へRelocateしたがSupply Radius 5 -> 5で実益0」のようなActionをPlayer/Agentが判断できる。

Hidden Zombie情報は一切含めない。

## 15.4 Queue Pressure

Checkpoint Branch Observationへ、Policy処理能力と現在Queueの圧力を理解しやすい公開情報として追加する。

候補:

```text
waiting + screening + approved
screeningCapacity
currentPolicyTurns
estimatedThroughput
arrivalIntervalRange
arrivalPeopleRange
queuePressureClass
```

将来乱数は公開しない。

# 17. Balanced Agent更新方針

Balanced Agentはv1.4で次を評価する。

## 17.1 Guaranteed Defeat

```text
Guaranteed Defeat Avoidance
> Immediate Combat Opportunity
```

をHard Priorityとする。

Food/Civilian Goods不足で健全民間人口0が確定する場合、対応可能なDomestic ActionをCombatより優先する。

## 17.2 Production Redundancy

- Resource別Single Point of Failureを評価する。
- 主力Farm 1施設依存時はSimple Farm建設を候補化する。
- 既存主力Facilityが危険な場合、冗長Facility確保・建設を評価する。

## 17.3 Fuel-aware Mobility

- 近距離移動と長距離移動のFuel差を評価する。
- National Guardの6Hex以降を高コストとして扱う。
- Supply外で次TurnにFuel切れになる進出を減点する。
- Horde Warningへの緊急展開はFuel Penaltyを上書き可能とする。

## 17.4 Forward Recon

- Horde Warning方向やFog外Threat探索にDrone Baseを評価する。
- Drone Visionだけを理由に重要なFood / Fuel / Defenseを犠牲にしない。

## 17.5 Supply Expansion Value

Checkpoint Actionは位置だけでなくProjected Supply Effectを評価する。

```text
Radius増加0
新規Supply施設0
Threat増加あり
```

の前進Relocateは低Priorityとする。

# 19. Horde Timing

Map拡大で入口からCapitalまでの距離が大きく変わる。

31×31推奨Mapでは東西南北入口から中央まで約15Hexとなり、現行Mapの約7Hexからほぼ2倍になる。

一方、Human UnitはMove 10へ高速化する。

このためHorde Cycle / Final Horde TurnをMap Sizeだけから単純比例で変更しない。

初期Simulationでは現行の、

```text
Horde Cycle = 5
Final Horde Turn = 30
Zombie Move = 現行
```

を維持した比較を必ず行う。

その後、少なくとも:

```text
Final Turn 30
Final Turn 35
Final Turn 40
```

を比較し、勝率、前Wave残存数、最大Visible Zombie、平均Battlefront距離、資源収支を確認する。

# 26. 設計意図

v1.4.xでは、v1.3.3で成立した、

```text
Checkpoint redundancy
Terrain selection
Combat Noise
Population / Infection / Economy
```

を捨てず、より大きな作戦空間へ拡張する。

最終的にPlayerが考えるべき関係は、

```text
Large Theater
↓
Mobility
↓
Fuel Endurance
↓
Supply Network
↓
Forward Infrastructure
↓
Reconnaissance / Food Redundancy
↓
Battlefield Selection
↓
Survival
```

となる。

重要なのは、Simple Farm、Drone、Wind、Fuelを独立した新機能として追加することではない。

- WindがFuelを発電から解放する。
- 解放したFuelで軍を遠距離展開できる。
- Checkpoint前進でSupplyが伸びる。
- Supply内にDroneを建てて先を見る。
- Supply内にSimple Farmを建てて主力Food拠点の喪失へ備える。
- Forecastによって「戦闘に勝っていても国家が死ぬ」状況をPlayerが理解する。

という一つのLogistics Systemとして成立させることをv1.4.xの中心目標とする。
